1. Feature Branch
 - 각 기능별 독립적인 브랜치 생성하여 작업
 - 서로의 작업에 영향을 주지 않음
 - 간단한 브랜치 전략을 사용하여 협업을 원할 때 적합
  → 기준 브랜치(Main or Master) 에서 feature/기능명 으로 브랜치 생성
  → feature 브랜치에서 작업 및 커밋
  → 기준 브랜치로 병합하기 전에 원격 저장소에 feature 브랜치 push
  → 코드 검토 후, 기준 브랜치에 feature 브랜치 머지
  → 머지 후 불필요한 feature 브랜치 삭제

2. Github Flow
 - 규모가 작거나 중간 크기의 프로젝트에 적합
 - 빠른 개발주기와 지속적인 배포에 초점
 - 지속적인 통합 및 배포를 원할때 유용
  → 기준 브랜치에서 새로운 브랜치 생성
  → 브랜치 명은 작업 내용을 설명하는 명칭
  → 기준 브랜치는 항상 배포 가능한 상태
  → 작업 브랜치에서 작업 후 Push
  → GIthub에서 PR 생성 후 코드 리뷰 요청
  → 코드 리뷰 완료 후 기준 브랜치에 머지, PR 종료

3. Git Flow
 - 프로젝트의 코드 관리와 릴리즈를 체계적으로 진행
 - 규모가 크고 복잡한 프로젝트에 적합
 - 여러 개발자들과 협업, 다양한 기능 및 릴리즈가 동시에 관리되어야 할 때 적합
 - Master : 프로덕션 환경에 배포되는 안정적인 코드가 저장되는 브랜치
 - Develop : 개발 중인 코드를 관리하는 브랜치
 - Feature : 새로운 기능 개발을 위한 브랜치(Develop 브랜치로부터 분기)
 - Release : 새로운 버전 릴리즈를 준비하는 브랜치(Develop 브랜치로부터 분기)
 - Hotfix : 긴급한 버그 수정을 위한 브랜치 (Master 브랜치에서 분기)
  1. 새로운 기능 개발
   → Develop 브랜치에서 Feature 브랜치 생성
   → 기능 개발 완료 후 Develop 브랜치로 머지
  2. 릴리즈 준비
   → Develop 브랜치에서 Release 브랜치 생성
   → 버전 번호 부여, 문서 및 배포 등 릴리즈와 관련된 작업 진행
   → Relase 브랜치를 Master 브랜치로 머지
   → 해당 커밋에 태그 추가하여 버전 명시
   → Relase 브랜치를 Develop 브랜치에 머지
  3. 긴급한 버그 수정
   → Master 브랜치에서 발견한 버그는 Hotfix 브랜치 생성해서 수정
   → 수정 완료 후 Master, Develop 브랜치로 머지
